# prompt-optimizer-magpie · 下一版做什么

**先验证改写能否减少用户返工，再决定首轮是否默认用 merged。** 对“把这个需求整理一下”，改写可能帮执行模型明确交付物；对“只列出要改的字段，先别改文件”，多补一个实施步骤就偏离了任务。两者在面板上都可能显示“改写成功”。产品要衡量的是交付改善、意图保真和多等的时间。

就 e0cc0c9 的能力，建议保留两条路径：首轮可比较 auto 与 merged；长线程中途另起新任务仍交给能判断上下文依赖的 auto，不能用首轮实验的结果替它做决定。精确缓存继续服务重试，规则回落与熔断继续保障故障时请求能发出去。以下 P0–P2 都可放在现有插件包内，复用本地文件与标准库，无需新服务。

## 值得做（P0/P1/P2）

| 优先级 | 需求 | 一句话设计草案与取舍 |
|---|---|---|
| P0 | 验证哪些请求值得改 | 用自备的完整脱敏样本覆盖模糊首轮、已清晰指令、追问及线程中的新任务；固定下游模型和任务条件，将原文、auto、merged 产生的执行结果打乱盲评，分别记「应放行却改写」「丢失或新增约束」「交付物更可用」的件数、分母及代表性反例，作为每次模板发布的验收依据。 |
| P0 | 让灰度数据回答“多等多久，换来了什么” | 在共同硬门之后、第一次模型调用之前分组，每个入组请求只记一条无正文终态摘要，含实验版本、组别、首轮/线程、实际模式、最终动作、缓存命中、模型调用次数和 hook 耗时；面板按组展示样本量、实际回写率、护栏放行原因及耗时 p95，避免把多条过程日志当作多个请求。 |
| P1 | 让维护者可以小范围放量和撤回 | 先选一个明确允许的 agent，确认其会话标识跨请求稳定后，按实验号和会话做固定分桶，缺失标识走基线并统计覆盖率；首轮保留原样直通组，与当前 auto、候选 merged 同期比较，维持重试分组，撤回候选只需把其比例调零。 |
| P1 | 让模板发布与回滚可复现 | 在生成模板时给模板、决策文案和 merged 协议生成一个内容版本，同时写进精确缓存键与终态摘要；这样在现有 60 秒默认 TTL 内发布、回滚或并行灰度都能区分结果，旧项自然过期。 |
| P2 | 按 agent 或目标模型花不同的等待预算 | 只有同类任务在盲评收益或耗时上持续分化时，才为明确的 agent／请求模型组配置一条覆盖规则，例如交互式 CLI 在剩余预算不足时发送原文，批处理首轮可试 merged；未知组合走全局配置，避免维护整张策略矩阵。 |

**放量判据。** 先约定可接受的额外等待和严重语义偏差；盲评发现把“只检查”改成“执行修改”就先修文案。只有同类首轮样本的交付质量达到约定、且线上调用数或延迟有收益，才扩大 merged。dryRun 适合看候选文本，但照样花模型调用，延迟基线必须用真正直通组。线上 hook 耗时只衡量插件这一段；没有显式结果反馈时，面板不能宣称任务完成率提升。

## 不建议做（理由）

| 候选 | 判断与替代方案 |
|---|---|
| 默认将长 prompt 分段、增量改写后拼接 | “除附录外都翻译”依赖跨段约束，分段还会倍增调用；保留完整输入与原样放行，只有客户端明确标出可编辑区和只读材料时，才考虑只改一段。 |
| 并行启动 decider 与 optimize 预热 | 判定为追问或 skip 时优化调用已付费，模板档位也还未知；若瓶颈确实是首轮的两次往返，先在同一批请求上比较 merged。 |
| 向下游 streaming 转发半成品改写 | 下游一旦收到前半段，末尾才发现约束丢失就无法恢复原请求；保留整段校验与一次替换，内部流式读取至多用于提前取消超限输出，不会让下游提前作答。 |
| 用 embedding 相似度复用另一条请求的全文 | “保留旧字段”和“删除旧字段”主题极近、交付相反，共享网关还可能带出别人的上下文；保留精确缓存，先用重试命中数据判断缓存是否值得继续投入。 |
| 按后续追问或沉默自动调模板 | “继续”可能表示满意，也可能说明上轮漏做；把获授权的典型案例加入盲评集，模板选择先由可复核的标签驱动。 |

## 需要平台支持

| 场景 | 最小平台契约与当前边界 |
|---|---|
| 多租户共用网关 | 宿主提供经过认证的租户标识并约束统计页访问，插件才能按租户隔离缓存、审计与实验；agent 名称不能证明身份，确需隔离时先用独立网关实例、数据目录及访问权限。 |
| 在线质量反馈闭环 | 宿主提供可关联的请求标识，并允许客户端显式反馈“保留原意／改偏了”或给出任务验收结果；插件按实验版本聚合，同时显示反馈覆盖率，无须保存新的用户正文。 |
| 与其他改写插件、子代理组合 | 由宿主提供可信的请求来源、插件执行顺序及已处理标记，明确谁可写用户正文；本地沿用已知 subagent／自身调用的跳过规则，用实际组合做顺序回放，不在用户消息中嵌入控制标记。 |

依据为当前分支的 hooks.mjs、lib/rewrite-cache.mjs、lib/stats-service.mjs、README.md 与 docs/design.md §5。设计文档列出了 ctx.session；各客户端的覆盖率、稳定性，以及真实流量中的质量和延迟收益均待验证。
